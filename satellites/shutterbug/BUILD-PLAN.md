# SHUTTERBUG BUILD-PLAN.md

**What this is.** The build plan for SHUTTERBUG, the single file mobile pixel art platformer where a photo of a room becomes the level. Written 2026-10-29 by the lead (Fable) from `DESIGN.md` v1.0 and `HANDOFF.md` v1.0, for Stephen's approval and for one Opus session to build from overnight, autonomously, with nobody answering questions. It has the seven sections HANDOFF section 5 lists, in that order, after a section 0 State block that the builder updates every time a task ships. DESIGN is ruled and is not edited by this plan; every place the plan reads DESIGN a particular way, or decides something HANDOFF left to Stephen, is marked `QUESTIONS.md Qn` inline and the plan proceeds on the recommendation written there.

**Who builds it, and how long the night is.** One Opus session, roughly 8 to 10 hours, two cores (one physical core: one headless Chrome at a time, no agent fan out), nobody awake. The task list in section 4 is therefore a strict sequence for one engineer: every task is 15 to 90 minutes, ends with a harness assertion or a screenshot that proves it, and leaves `index.html` loading without a page error with the title screen reachable. **Vocabulary.** "Cell" is a 16x16 game pixel square of the 24x48 grid. "Game px" is one pixel of the 384x768 world. "CSS px" is what the browser lays out in; "device px" is the physical dot. "Standable" is an open cell whose cell below is solid or a one way platform. "Core" is the pure deterministic code the harness also runs; "shell" is everything that touches the DOM, time or the player. "Gate" is one runnable check that prints an OK line `tools/check.js` greps for. "Watched red" means the gate was seen failing on a deliberately broken copy before it was trusted. "Mutant" is the named row in `tools/redwatch.js` that breaks that copy.

### 1.2 Core versus shell: the line

Core (blocks 1 to 8) is the set the harness evaluates. Every core block has exactly this shape, and no other top level statement:

```js
(function (SB) { 'use strict';
  /* module body; attaches SB.<name> = { ... } */
})(globalThis.SB || (globalThis.SB = {}));
```

In the browser `globalThis` is `window`, so `window.SB` is the game's core; in the harness's `vm` context `globalThis` is the context, so the harness reads `ctx.SB` after the last block runs. No top level `const`, `let`, `class` or `function` in any block: classic scripts share top level lexical declarations and a second declaration throws in the browser. The lint allows the exact IIFE tail above and forbids any other `globalThis` token.

Core may reference: ES2020 syntax, `Math` except the poisoned names below, typed arrays, `Array`, `Object`, `Map`, `Set`, `Number`, `String`, `JSON`, `Error`, and `SB`. Allowed `Math`: `floor ceil round trunc abs min max sign sqrt clz32 imul fround`. Core may not reference, and `tools/lint.mjs` fails the build if any core block contains the token (word boundaries, regex over the extracted block): `window`, `document`, `navigator`, `location`, `self`, `parent`, `postMessage`, `localStorage`, `sessionStorage`, `indexedDB`, `fetch`, `XMLHttpRequest`, `setTimeout`, `setInterval`, `requestAnimationFrame`, `queueMicrotask`, `performance`, `Date`, `Intl`, `Math.random`, `Math.sin`, `Math.cos`, `Math.tan`, `Math.atan2`, `Math.exp`, `Math.log`, `Math.pow`, `Math.hypot`, `Math.cbrt` (and the rest of the transcendental list in section 1.3), `toLocale`, `console`, `alert`, `eval`, `Function`, `Image`, `ImageData`, `ImageBitmap`, `createImageBitmap`, `OffscreenCanvas`, `AudioContext`, `crypto`, `btoa`, `atob`, `TextEncoder`, `import`, `require`, `process`, `Promise`, `async`, `await`, `instanceof` (core tests typed arrays with `ArrayBuffer.isView` and arrays with `Array.isArray`: a structured clone from the harness realm fails `instanceof` for a realm reason, section 1.3), the `**` operator (`Math.pow` by another name), `localeCompare`, `normalize`. The scan runs over the block with its comments and string literals stripped first (a small state machine; the `vm` parse already proves the block is whole), so the words `parent`, `self`, `Date` or `Image` in a comment never fail the build. The lint also forbids a bare `1152`, `384` or `768` in a core block outside `SB.GRID`. Watched red by adding `Date.now()` to a copy of `core-sim`. The harness's poison prelude (section 1.3) makes the same slips throw at run time.

Core numeric rule: **every number that persists in `State` is an integer.** Positions and velocities are integer subpixels (`SB.K.SUB = 256` per game px, so one cell is 4096 subpx). Timers are integer frames. The RNG state is a uint32. That is what makes `sim.hash` bit exact across V8 in Chrome, V8 in Node and JavaScriptCore on an iPhone without any float policy; the few floats the core keeps (Otsu's variance, the arc table derivation at load) use only `+ - * /` and `sqrt`, which IEEE 754 fixes bit for bit on every engine, and `serialize` throws on any non integer field so a float leak is a failure, not a drift. Bobbing, hops and orbits use integer triangle waves and tables, never `Math.sin`.

Shell blocks may use anything the browser offers. Shell never reaches into `State` to mutate it: it calls `sim.step(state, word)` and reads the state afterwards. `render` reads `state` and `level`, never writes either. `save` is the only block that touches `localStorage`. `audio` creates the `AudioContext` inside the first `pointerdown` and never before.

### 1.3 Sharing the core verbatim with harness.js (no build step)

There is one copy of the core and it is the one in `index.html`. The harness does not import a module; it reads the page. The mechanism below is committed and proven on this box in Node 24.21 (`tools/shutterbug-tests/core-loader-proof/`, `node harness.js` there prints `CORE LOADER OK`); hour one of the night copies it, it does not rediscover it.

**The marker.** A core block is exactly `<script id="core-NAME" data-core>` on its own line, the body, then `</script>` on its own line. The extraction is one regular expression, the same literal string in `harness.js` and `fixtures/make.html` (the lint asserts the two literals are byte identical). It needs LF line endings and tags at column zero: the lint asserts the page holds no `\r` and no BOM, forbids `<!--` and `<script` inside any script block, and matches `</script` case insensitively (the HTML tokenizer does); when zero blocks match, the harness prints `no core block matched: LF line endings and column zero tags required` instead of an empty block order.

```js
const CORE_RE = /^<script id="(core-[a-z]+)" data-core>\n([\s\S]*?)\n<\/script>/gm;
```

**The order assertion.** The harness collects every match in document order and asserts the id sequence equals exactly `core-ns, core-rng, core-palette, core-record, core-pipeline, core-reach, core-features, core-sim`, and that no block contains the text `</script` anywhere (a string literal with it would end the block early in the browser too). A missing, duplicated or reordered block is a harness failure before anything runs.

**Evaluation in Node 24.** Each block runs as its own `vm.Script` in one fresh, hostile context, with a filename and a line offset so a stack trace points at the real line of `index.html`:

```js
const fs = require('node:fs'), vm = require('node:vm'), path = require('node:path');
const html = fs.readFileSync(PAGE, 'utf8');               // PAGE defaults to index.html beside harness.js; --page <file> points elsewhere
const blocks = []; let m;
while ((m = CORE_RE.exec(html))) blocks.push({ id: m[1], src: m[2], index: m.index });
const ctx = vm.createContext({});                         // a fresh realm: no console, setTimeout, process, require, fetch, window
new vm.Script(POISON, { filename: 'poison.js' }).runInContext(ctx);
for (const b of blocks) {
  const lineOffset = html.slice(0, b.index).split('\n').length;
  new vm.Script(b.src, { filename: 'index.html#' + b.id, lineOffset }).runInContext(ctx);
}
const SB = ctx.SB;
```

This loader is factored into `tools/core-loader.js` exporting `loadCore(pagePath) -> SB`, used by `harness.js`, `tools/redwatch.js` and every gate that needs the core in Node: one Node loader, one browser loader (`make.html`'s), zero copies of the mechanism.

`POISON` makes impurity a runtime failure rather than a review opinion (a fresh context does have `Math.random` and `Date`; the judges verified that a bare context catches nothing, so the prelude is not optional):

```js
Math.random = function () { throw new Error('core touched Math.random'); };
for (const f of ['sin','cos','tan','asin','acos','atan','atan2','exp','expm1','log','log1p','log2','log10','pow','cbrt','hypot','sinh','cosh','tanh','asinh','acosh','atanh'])
  Math[f] = function () { throw new Error('core touched Math.' + f + ' (not correctly rounded, differs across engines)'); };
Object.defineProperty(globalThis, 'Date', { get() { throw new Error('core touched Date'); } });
Object.defineProperty(globalThis, 'Intl', { get() { throw new Error('core touched Intl'); } });
Object.defineProperty(globalThis, 'console', { get() { throw new Error('core touched console'); } });
```

`window`, `document`, `navigator`, `localStorage`, `location`, `fetch`, `performance`, `requestAnimationFrame`, `setTimeout`, `btoa`, `TextEncoder` and `crypto` do not exist in the context, so a reference throws `ReferenceError` the first time the harness runs that line, with the page's line number. `console` DOES exist in a fresh context (V8 supplies one; verified on this box 2026-10-30, `typeof console === 'object'`), which is why the prelude poisons it too; the proof folder's README says it does not exist and this sentence corrects it.

**Realm note for the builder.** Typed arrays made inside the context belong to another realm: `instanceof Uint8Array` is false in the harness. Never use `instanceof` on core outputs; compare by length and bytes. The same holds in the other direction: `H-sim-6` and `H-pipe-8` pass structured clones from the harness realm INTO the core, where `x instanceof Uint8Array` is false for a realm reason while `ArrayBuffer.isView(x)` is true (verified on this box 2026-10-30), which is why `instanceof` is a forbidden token in core (section 1.2). Pass fixtures in as strings (the hex rows of section 2.1) and let `SB.record.fromJSON` build the arrays inside the core realm. `JSON.stringify` and `structuredClone` work across realms.

**`fixtures/make.html`** reuses the core the same way a browser can: `fetch('../index.html')`, the identical `CORE_RE`, then `new Function(src)()` per block in order (this works because every block is an IIFE attaching to `globalThis.SB` and declares nothing at top level; a top level `const SB` would not survive separate `Function` bodies), plus the `data-tool` block `shell-capture` the same way. Two loaders, one source, zero copies.

**The same core in the page.** In the browser the blocks are ordinary classic scripts; nothing is extracted. Cross realm parity is proven by replays, not by shipping test code: `SB_DEV.replay(script)` runs a recorded input script through a fresh sim in the page and returns the hash, and the `replay` browser gate asserts it equals Node's (section 5.4). No lab room, macro or test lives in the served file.

### 1.4 `SB.GRID`, `SB.GRID_PRESETS`, `SB.TUNING`, `SB.K`

`core-ns` holds all of them, deep frozen (every nested array and object: `Object.freeze` is shallow and `TUNING.FODDER_CELLS[0] = 9` would otherwise be legal; `H-ns-2` asserts `Object.isFrozen` on every nested value). `GRID` is the single grid constant DESIGN 3 asks for, a preset switch so the 36x64 fallback is one line plus a corpus regeneration (QUESTIONS Q43):

```js
SB.GRID_PRESETS = Object.freeze({
  A: Object.freeze({ W: 24, H: 48, CELL: 16, HERO_W: 12, HERO_H: 16, VIEW_ROWS: 40 }),   /* ruled */
  B: Object.freeze({ W: 36, H: 64, CELL: 10, HERO_W: 8,  HERO_H: 12, VIEW_ROWS: 64 })    /* the fallback, Stephen's call only */
});
SB.GRID = SB.GRID_PRESETS.A;
```

Everything else derives from `GRID`: world px `W*CELL` by `H*CELL`, record length `W*H`, the viewport in whole rows, the reach tables (recomputed from the kinematics at load for the cell size). A level carries its own `h` (48, or 96 for Double Exposure; QUESTIONS Q19): every core function takes `w, h` from the level, never from `GRID`, except capture and the record validator.

`TUNING` carries every number in DESIGN by name, in DESIGN's units (cells, px per frame, frames, seconds), grouped by DESIGN section, so the reviewer can diff it against DESIGN and the builder types each number once. A number from DESIGN appearing anywhere else in a core block is a bug (the lint lists every bare numeral above 16 in `sim`, `pipeline`, `reach` and `features` outside `TUNING` as a warning block in the gate output; `256`, shifts and masks are legitimate, so it warns, never fails). ### 1.5 The loop, input, the phone, the render budget, the PWA, the share flow

**Fixed step with an accumulator (HANDOFF rule 3).** `shell-boot` runs `requestAnimationFrame(frame)`. Per frame: `dt = min(now - last, 100)` (a tab switch never produces a catch up storm; after 100 ms away the game simply pauses), `acc += dt`, then `while (acc >= 16.6667 && steps < 4) { word = input.sample(); sim.step(state, word); acc -= 16.6667; steps++; }`; if four steps run and `acc` is still over a step, `acc = 0` and the frame is counted as a stall in `SB_DEV.perf()`. Then `render.draw(state)`. The sim never sees `now`; it sees step counts. Nothing in the loop calls `Date`; it reads the `requestAnimationFrame` timestamp.

**Input sampled once per sim step.** `shell-input` keeps a raw latch: for each of `left, right, jump, dive` a `held` boolean updated by pointer, key and gamepad events, and a `pressedSince` counter incremented on every down edge. `input.sample()` builds one integer word (section 2.6): held bits `L=1 R=2 A=4 B=8`, pressed edge bits `A_TAP=16 B_TAP=32` set when any down edge happened since the previous sample, then clears the edge counters. A tap shorter than one step (touch screens report at 120 Hz) still registers as exactly one tap step with `held` false, which is what the jump buffer and the dive tap need. Two samples are never taken in one step and one sample is never reused across steps; the word is also what the replay recorder appends, so a replay is the exact sequence the sim consumed. Gamepad is polled inside `sample()` (d pad or left stick with a 0.5 dead zone to the rocker, south to A, west to B), never between steps; it arrives in T1.14. A word with both `L` and `R` set (keyboard left plus right, or a gamepad merged with a key) reads as neutral: no run, the decel applies (section 2.6).

**The rocker and the buttons.** The control strip is DOM, not canvas, so the layout gate can measure it with `getBoundingClientRect` and press it with real touch events. Rocker: one element at the strip's left, starting at `x = CHIP_RESERVE_PX` (120 CSS px) because the fleet's music chip owns the bottom left 120x120 of every page (section 1.6, QUESTIONS Q48: DESIGN 4.1's "bottom left" moves right by the reservation), two zones with a 16 px visible neutral gap; `pointerdown` and `pointermove` with `setPointerCapture` map the pointer's **current** x to left, neutral or right, so a thumb slides between zones without lifting (DESIGN 4.1); `pointerup` and `pointercancel` release. A and B: two elements bottom right, outer and inner, each 64x64 CSS px on phones 390 and wider and 56x56 at 360 (DESIGN's minimum; at 360 the strip is exactly 120 + 128 + 112 wide with no margin); at 320 wide the reservation is released and the rocker starts at `x = 0` (the chip then lands where the fleet's search puts it; the layout gate prints its rect at 320 and asserts it at 412, 390 and 360); hit areas extend to the strip's full height outside the reserved box. `touch-action: none` on the strip and the canvas, `user-select: none`, `overscroll-behavior: none`, `-webkit-tap-highlight-color: transparent`, `contextmenu` suppressed. Multi touch: each verb tracks its own `pointerId`, so a jump during a rocker hold works. Mirrored layout flips the strip with one class (A and B from `x = 120`, the rocker at the right; the reserved box stays bottom left and empty in both layouts). Hint glyphs (DESIGN 5.3) are drawn inside the strip beside the control they name. Keyboard for desktop: arrows, Z = A, X = B, space = A.

**Integer scaling, exactly.** The play canvas backing store is `384 x (VIEW_ROWS*16)` game px: one canvas pixel is one game pixel and the render never scales. CSS does the enlargement with `image-rendering: pixelated` and a CSS width chosen by `render.fit()`, re run on `resize` and `visualViewport.resize`:
- CSS width 768 or more: canvas CSS width 768 (2x). Otherwise CSS width 384 or more: canvas CSS width 384 (1x), centred, side gutters in the frame colour. These are the integer cases DESIGN 3 rules and the layout gate asserts the canvas CSS width is exactly 384 or 768 there.
- CSS width under 384 (a 360 wide phone, in the plan's own phone matrix): there is no integer solution. Default: the canvas CSS width is `100vw` and the browser shrinks 384 to 360 (0.9375; at device pixel ratio 3 that is 2.8125 device px per game px: every sixteenth device column is dropped, invisible at arm's length). This is the one exception to "never fractional scale" and it is Stephen's call, QUESTIONS Q5: the alternative (a 24 px horizontal camera window, the world cropped to the screen and the camera following the hero sideways by up to 24 px) is built behind the dev query `?fit=crop` so the morning report can show him the same sample room frame both ways at 360x800, side by side. Integer scaling holds exactly on every phone 384 px or wider.
- Height: `top strip 36 + play + control strip 168` must fit `100dvh` (fallback `innerHeight`, re measured on `visualViewport.resize`). `VIEW_ROWS = clamp(floor((h - 36 - 168) / 16), 20, 40)`: 40 rows on a 390x844 or 412x915 phone, 36 on 360x780, 22 on a 320x568 iPhone SE (364 px of play area; a floor of 28 would have needed 652 px on a 568 px screen, so `VIEW_ROWS_MIN` is 20, QUESTIONS Q6). Spare height goes to the control strip (it grows from 168), never to the play area, so the frame yields to the controls and the hero's 60% camera line stays in the same place on every phone (QUESTIONS Q6).
- Safe areas: `viewport-fit=cover` in the meta viewport; `padding-bottom: env(safe-area-inset-bottom)` on the strip; the canvas never sits under the home indicator.

**Canvas performance at 60 fps on a mid range phone.** Three layers, one `drawImage` each plus sprites:
1. `static` (offscreen canvas 384 x worldH): the quantized backdrop at 60% contrast, Ink outlines on solids, Glare top edges on platforms, ice edges, vine and pipe overlays, film tabs. Built once per level by the develop reveal's last beat; the reveal itself draws from a second offscreen `photo` layer (the cropped photo at 384x768, kept only until the reveal ends and then released; photos never persist, DESIGN 1).
2. `play` (the visible canvas): per frame `drawImage(static, 0, camY, 384, viewH, 0, 0, 384, viewH)` with the integer `camY` that `render` keeps (the camera is render state, never `State`: `render` recomputes `camY = clamp(hero.y / SUB - (viewH * 3 / 5 | 0), 0, worldH - viewH)` from `state.hero.y` each frame, so the sim hash is identical on a 22 row SE and a 40 row Pixel and the cross engine replay of section 5.4 compares engines, not screens; nothing in the sim reads the camera), then every live sprite at integer coordinates from the `atlas` (section 1.7's pixel strings rasterised once at boot into one offscreen canvas), then effects, then the beacon.
3. The frame, strips, hearts, DP counter and hints are DOM over and around the canvas, repainted only when their text changes (`textContent` set on change, never per frame).

Budget: with 4 enemies and 8 projectiles the per frame work is one 384x640 blit plus under 40 `drawImage` calls of 16 to 24 px sprites. No `getImageData` on the hot path, no `ctx.save/restore` per sprite, no gradients, no shadows, no text on canvas, no allocation inside `draw` (sprite rects preallocated), no `Math.round` on a float camera because `render`'s camera is an integer. Animation frame index is `floor(state.frame / 5)` (12 fps hold at 60 Hz). Screen shake is an integer offset on the blit, at most 2 px, only on dive landings and boss hits. The perf gate (section 5.6) measures `step` and `draw` around `SB_DEV.perf()` and fails if the 95th percentile of `step + draw` on this box exceeds 4 ms (swiftshader on two cores is far slower than a phone's GPU; the phone number is the morning's) and if the pipeline exceeds 50 ms in the page for the sample room.

**The PWA.** `manifest.json` with `"start_url": "./"`, `"scope": "./"` (no `id` member: it defaults to the resolved `start_url`, so a moved or vendored copy keeps its own install identity, NEW_SATELLITE_BRIEF rule 2), `display: standalone`, `orientation: portrait`, `theme_color` and `background_color` the palette's Soot, icons `./icons/icon-192.png`, `./icons/icon-512.png`, `./icons/icon-maskable-512.png` (generated by `tools/icons.mjs` from a pixel string of the Shutterbug, PNG written with Node's `zlib`, no dependency). `sw.js`: `const CACHE = 'shutterbug-v<N>'`; precaches `./`, `./index.html`, `./manifest.json` and the three icons one by one (never `addAll`, which fails the whole install on one miss); caches `./music/*` lazily on first play (DESIGN 11; the game's own seven tracks under its own scope, which is a different thing from the fleet's `/music/` library that the root worker is forbidden to cache, QUESTIONS Q37); only ever deletes `shutterbug-*` caches (`caches.keys()` is origin wide and every satellite shares the origin); navigations refetch with `cache: 'no-cache'` and an 8 s timeout, fall back to the cached shell, and every fetch path settles with a real `Response`; its fetch handler begins with `if (!req.url.startsWith(self.registration.scope)) return;` before any `respondWith`, so the fleet's root files (`/music-unlocks.js` and the three it loads, section 1.1) are never intercepted, cached or answered: do not copy gerplunk's same origin branch (it caches any same origin 200, the include with it) nor its unconditional registration block. ### 1.7 Sprites, pixel strings, and `SB_DEV`

Sprites are inline pixel strings in `shell-render`: one string per frame, rows separated by `/`, one character per pixel from a 17 character key (`.` transparent, `0`..`9`, `a`..`f` the palette index). The atlas builder rasterises every string once at boot into one offscreen canvas and records `{x, y, w, h}` per name. Under 40 named sprites (DESIGN 11; frames per sprite are unlimited: the lint counts names, never frames) and the lint asserts every row of a sprite has the same length and every character is in the key. ## 2. The level record and run state schemas, with versions

Every persisted or shared shape carries a version integer `v`. A reader that meets a version above its own refuses with a plain sentence (`This room was made by a newer Shutterbug. Update and try again.`) and keeps the bytes; a version below its own is migrated by an explicit pure function per step (`migrate1to2` and so on) that the harness tests against a stored fixture of the old shape. Nothing is persisted that is not listed here, and no photo, crop, bitmap or data URL is ever persisted (the lint greps `shell-save` and `shell-ui` for `toDataURL` and `toBlob` and fails on any hit outside the share sheet's grid preview).

### 2.1 Level record v1 (DESIGN 6.13)

In memory, the only thing ever persisted or shared:

```js
{ v: 1, w: 24, h: 48, mode: 0, focal: null, pal: Uint8Array(1152), pal2: null }
// mode: 0 normal, 1 Negative, 2 Double Exposure (pal2 is the second grid, same length; the built level then has h = 96)
// focal: null or a cell index 0..w*h-1 (the chest cell chosen by the focal tap)
// pal[i] in 0..14, row major, i = y*w + x, row 0 is the top of the room; index 15 (the film tab cream) is reserved for repairs and never appears in a record (QUESTIONS Q13)
```

**JSON form** (fixtures, the save's recent rooms and run, export, `make.html`'s download): the grid as 48 strings of 24 lowercase hex digits, one per row, so a human can read a room in a diff; every reader in the system (harness, make.html, the save, the share codec's `fromJSON`) reads this one shape:

```json
{ "v": 1, "w": 24, "h": 48, "mode": 0, "focal": null,
  "rows": ["555555555555555555555555", "...47 more rows..."], "rows2": null }
```

`record.validate(json)` fails on: `v !== 1`; `w, h` not the grid preset; `rows.length !== h` or any row not exactly `w` hex digits; any digit `f` (index 15); `focal` outside `null` or `0..w*h-1`; `mode` outside 0..2; `mode === 2` without `rows2` of the same shape; `mode !== 2` with a `rows2`. `fromJSON` builds the typed arrays inside the core realm; `toJSON` is its exact inverse (`H-rec-1`).

**Packed form** (`record.pack`), the share payload: big endian header, two palette indices per byte, high nibble first, no padding:

| Offset | Bytes | Field |
| --- | --- | --- |
| 0 | 1 | `v` = 1 |
| 1 | 1 | `w` = 24 |
| 2 | 1 | `h` = 48 |
| 3 | 1 | `mode` 0..2 |
| 4 | 2 | `focal + 1` as uint16 (0 means none) |
| 6 | `w*h/2` = 576 | `pal` nibbles: `pal[2k] << 4 | pal[2k+1]` |
| 582 | 576 | `pal2`, mode 2 only |

Sizes: modes 0 and 1 pack to 582 bytes, which is divisible by 3, so base64url (RFC 4648 section 5 alphabet, no `=`) is exactly **776 characters**; the share string is `v1.` + that (779); the URL `https://lucidwinds.com/satellites/shutterbug/#v1.<...>` is **825 characters**, within DESIGN 10's "about 800" (QUESTIONS Q2 notes the path differs from DESIGN's `/shutterbug/`). Mode 2: 1158 bytes, 1544 characters, a 1593 character URL. `record.encode` is total; `record.decode` returns `null` (never a partial record, never a throw into the UI) on: wrong decoded length (anything but 582 or 1158), `v` not 1, `w`/`h` not the preset, `mode` over 2, `focal` out of range, a nibble of 15, any character outside the alphabet. The base64url table is hand written in `core-rng` (no `btoa`), so the harness and the page encode identically. A single character corruption in a pasted code yields a different valid grid rather than a refusal; a checksum byte is the v2 record's first candidate if that ever matters, and the codec is versioned for exactly that.

**Seed** (DESIGN 6.12): `seedOf(rec) = fnv1a32(pal bytes, then pal2 bytes for mode 2)`, over the raw index bytes (one byte per cell), so the seed depends on the grid and nothing else: `mode` and `focal` change the build, not the seed (`H-rec-4`). The seed is derived, never stored, so a shared grid is self contained. Known answers the harness asserts: `fnv1a32Str('')` = `0x811c9dc5`, `fnv1a32Str('a')` = `0xe40c292c`; `mulberry32(1)` first two draws `0.6270739405881613`, `0.002735721180215478`.

### 2.2 Level (derived, never persisted)

`pipeline.build(record, opts)` returns either `{ needsCrop: true, why: 'unreachable' | 'repair-too-large' | 'repair-failed' | 'route' }` or a `Level`. `opts`: `{ biome: null | 0..4 (harness override), firstRoom: bool, lastRoom: bool }`. Every field is a deterministic function of the record and `opts`; listed so the harness can hash it and the renderer knows what exists. `levelHash` is pinned exactly: `pipeline.FIELDS` beside `sim.FIELDS` declares the order and `pipeline.serialize(level) -> Int32Array` walks it (`w, h, seed, biome, negative, otsuT, solid, plat, tab, slick, sticky, trap, spawn, exit, beacon.idx`, the landmarks as sorted cell lists, the ascent's node list, the feature placements as indices: specks, chest, scroll, blueprint, enemies as kind plus index, trap cells, door, boss cells, then `repair.tabs` and `degraded` as rung ids); `levelHash` is `sim.hash`'s two FNV passes over those bytes, and `H-pipe-8` perturbs each field the way `H-sim-7` does, so two correct implementations hash the same and a cross realm or cross page comparison compares something pinned:

```js
{

  stand: Uint8Array, reach: Graph, ascent: { ok, nodes: [], edges: [], reasons: [] },   // section 3
```

### 2.5 Sim state v1 and the state hash

`sim.FIELDS` is the declared, ordered schema of the whole sim state: every path, its type (`i32`, `bool`, `i32[]`, `u8[]`, `obj[]` with a nested schema) and nothing else is allowed in the state. `serialize(state)` walks `FIELDS` in order into an `Int32Array` (`i32`: assert `Number.isInteger(v)` and `-2^31 <= v < 2^31`, else throw naming the path; `bool`: 0 or 1; arrays: the length then the items; nested objects by their schema). Floats: v1 declares no float field; if a future version does, type `f32` writes `Math.fround(v)` through a shared `DataView` with NaN canonicalised to `0x7FC00000` and `-0` to `+0`, so the same value hashes the same on every engine. `hash(state)` is two FNV-1a-32 passes over the serialized bytes, pass one from the basis `0x811c9dc5` and pass two from `0x050c5d1f`, the words written through one `DataView` with `littleEndian = true` (an `Int32Array` view would be platform order), printed as 16 hex characters. The RNG state is a field. Timers, cooldowns, i frames, enemy phases, the projectile pool, the boss's alive mask, loot taken flags and the hero's every counter are fields.

```js
{ v: 1, frame: int, rng: uint32, biome, negative, firstRoom: 0|1, lastRoom: 0|1,
  hero: { x, y, vx, vy /* sub units */, facing: -1|1, ground: 0|1, wall: -1|0|1, sticky: 0|1, coyote, buffer, held: 0|1, rising: 0|1,
          dive: 0|1|2 /* none, dive, hold dive */, dash: frames, dashI: frames, iframes, hearts, heartsMax, vigor, focus, grit, scrolls,
          slots: [jumpId, diveId, charmId] /* 0 = none */, cd: [jumpCd, diveCd, charmTick], squash: int, anim: int, lastStand: idx, secondWind: 0|1, thickSkin: 0|1, shake: int },
  enemies: [{ kind, x, y, vx, vy, hp, state, timer, dir, home: idx, elite: 0|1, frozen, stunned }],   // fixed order; a dead enemy keeps its slot with hp 0
  proj: [{ kind, x, y, vx, vy, ttl, dmg, live }],                                                     // PROJ_MAX slots, lowest free first
  loot: [{ kind, idx, taken: 0|1 }], chest: { idx, open }, scrollsOffered: [a, b] | null, door: { idx, entered },
  traps: { phase: int }, boss: null | { cells: Uint8Array, hp, hpMax, phase, timer, intro, telegraph },
  room: { dp: int, blueprints: [ids], exitLit: 0|1, cleared: 0|1, dead: 0|1, deaths: int } }
```

The camera is not a field: `camY` is render state (section 1.5), derived from `hero.y` and the phone's `VIEW_ROWS`, so the hash never depends on the screen. The coverage gate (`H-sim-7`): for every entry of `FIELDS` the harness perturbs that field in a fresh state by one unit (or flips a flag) and asserts the hash changes; it asserts `Object.keys(state)` and each nested object's keys equal the declared lists; it runs 600 steps and asserts no key appeared that is not declared. A field added to the sim without being hashed fails this before anyone notices a desync.

### 2.6 Input word and replay script v1

One integer per sim step: held bits `L=1 R=2 A=4 B=8`, edge bits `A_TAP=16 B_TAP=32` (set for exactly one step when the shell saw a press since the last step), and bits 6..9 a 4 bit `CHOICE` field (0 none, 1 and 2 pick offer A or B, 3 take, 4 leave, 5..15 reserved) consumed by `sim.step` on the step it appears and recorded like any other word: while `state.scrollsOffered` (or a pending compare or shop offer) is non null the sim ignores the movement bits until a choice word arrives, so the shell's sheet is a view of sim state, the loop keeps stepping, and the shell never writes a stat into `State` (section 1.2; `H-sim-19`, mutant `CHOICE_VIA_SHELL`, T1.6). `L` and `R` both set reads as neutral (no run, the decel applies). A replay stores runs of equal words:

```json
{ "v": 1, "fixture": "sample-room", "mode": 0, "biome": null, "opts": { "hearts": 4, "loadout": null },
  "steps": 1800, "runs": [[12, 0], [1, 20], [30, 6], [60, 0]],
  "golden": { "hash": "9a1f3c07e2b8d410", "at": 1800, "why": "regold 2026-10-30 T0.13b: first golden" } }
```

Each run is `[count, word]`. The shell records the same words during play (`SB_DEV.recording()`), so a bug seen on a phone can be replayed in Node from the record and the script. A golden changes only through `node harness.js --regold --why "..."`, and the why lands in the file and in PROGRESS.md; a golden that changed without a why is a review finding.

## 3. The reach model as a spec the sim must satisfy

The reach graph is DESIGN 6.8's single source of truth: repair uses it, the exit choice uses it, the route score uses it, feature placement reads it, and the harness bot walks it. The sim is obliged to be **at least as generous**: every edge the model declares, a player (and the bot) can perform in the sim from a resting stance. The model is allowed to be stingier than the sim (it is, on purpose, by a cell here and there; it ignores corner forgiveness, air control past the table and the exact parabola); it is never allowed to be more generous. This section is the contract; section 3.9 is the assertion that fails.

### 3.1 Cells and stances

- Grid coordinates `(x, y)`, `x` in `0..w-1`, `y` in `0..h-1`, row 0 at the top. Cell index `i = y*w + x`. Out of bounds is solid (walls on both sides and a ceiling above row 0 for clearance), except that row 0 is always open and row `h-1` always solid (DESIGN 6.3).
- `open(i)`: `solid[i] == 0`.
- `plat(i)`: `plat[i] == 1`; the cell is open and its top edge is a one way surface (DESIGN 6.4: a run of at least `PLATFORM_RUN_MIN` surface cells; a surface is `open(i)` above and (`solid` below or a palette luminance drop over `EDGE_DROP_L`); runs over open cells become `plat`, runs over solid cells are just solid tops).
- `standable(i)`: `open(i)` and (`solid(i+w)` or `plat(i+w)`). The hero's body is in the cell; its feet rest on the top edge of the cell below. A one wide solid pillar top is standable; a floating surface only as part of a one way run. The floor row is solid so every open cell on row `h-2` is standable, which is where spawn is (DESIGN's "row 46, two above the floor", QUESTIONS Q10).
- `slick(i)`: Frost only, the surface under `i` belongs to a one way run of width at least `FROST_SLICK_MIN_W`. The two end cells of a slick run are **not** standable for the model (the one cell slide carries the hero off them); interior cells are.
- `wallcontact(i, side)`: `open(i)`, not standable, and `solid(i + side)` with `side` in `{-1, +1}`. A full height side contact in the same row; the corner rule (DESIGN 4.2: a 2 px overlap never arms a slide) lives in the sim, which arms a slide only with at least `HERO_H - CORNER_PX` = 14 px of vertical overlap against the solid's side and the rocker toward it. The graph never creates a contact from a corner because contacts are whole cells.
- `stickycontact(i, side)`: as `wallcontact` but `sticky[i + side] == 1` (Overgrowth vines, Deep pipes). Touching it stops the fall without the rocker.
- `trap(i)`: a trap field cell; never a node. `safe(i)`: standable, not a trap, not a slick end cell, and outside every enemy envelope (section 3.7).
- Stance for an edge's start: the hero grounded, horizontally centred in the cell (hitbox centre at `x*16 + 8`), `vx = 0`, facing either way. For a wall contact start: the hero touching the wall at the cell's vertical centre, sliding, rocker toward the wall. The bot's `settle` macro produces these stances (section 5.2).

### 3.2 Profiles and tables, derived from TUNING, clipped to DESIGN

`reach.tables(K, biome)` steps the hero equations of section 1.4 with no geometry and derives, for each profile, the landing table and the corridor. The harness asserts the tables against values it computes itself from `TUNING` by the same stepping (`H-reach-1`), so a `TUNING` edit changes both or the gate goes red; the numbers below are what the frozen `TUNING` gives on this box (2026-10-29), for the reader and for the known answer test that hard codes them (`H-reach-1b`, so the code's derivation is checked against the plan, not against itself). The known answers live in `fixtures/tables.json`, regenerated only by `node harness.js --retable --why "..."`, which prints the diff; the why goes in PROGRESS.md; a `TUNING` retune at 2 a.m. (the sanctioned fix for a red lab) is followed by `--retable` in the same commit, and the morning report lists every retable. The table below is at the `TUNING` frozen on 2026-10-29; the file is the truth after a retune.

Profiles: `FULL` (A held through the apex, rocker held in the jump direction from takeoff), `MID` (A held 4 frames), `TAP` (A held 1 frame), `WALL` (wall jump: `WALL_V` up, `WALL_JUMP_LOCK` = 10 frames of `WALL_JUMP_PUSH` away from the wall, then the rocker held away), `STICKY` (from a sticky contact: `STICKY_JUMP_V` straight up, no rocker: DESIGN 4.2 "straight up 4 cells, no push off"). Deep variants use `DEEP_JUMP_V` on the rise and `DEEP_FALL_MULT` on the fall gravity and terminal.

**Landing table** `maxAcross[profile][dy]` for `dy` cells up (0..5): the largest `dx` such that on the first descending frame where the previous frame's feet were at or above `16*dy` and this frame's feet are at or below it (the one way landing rule), the 12 px hitbox overlaps the target cell `[16*dx, 16*dx+16)` by at least `LAND_OVERLAP_PX`. Any `dx` from 0 to that maximum is reachable (the player releases the rocker earlier; the 4 frame decel makes every intermediate distance available). The table is then clipped to DESIGN's cone caps `JUMP_UP`/`JUMP_ACROSS` (4, 5), `WALL_UP`/`WALL_ACROSS` (3, 4), and for Deep `JUMP_UP + DEEP_EXTRA_UP` (5) with the across cap unchanged (DESIGN gives Deep no across number; QUESTIONS Q22).

| MID | 52.7 px | 29 | none | none | dx 3 | dx 4 | dx 5 | dx 5 |

Targets below the takeoff row (`dy < 0`) are reached by `JUMP_DOWN` (the same arc continued; dx 6 at one row down, 7 at four rows down, 8 at eight) and by `FALL` (section 3.6).

**Corridor** `corridor[profile][dx][dy]`: the set of cells `(k, r)` (`k` columns in the jump direction, `r` rows above the takeoff row, both relative) that the 12x16 hitbox occupies at any frame from takeoff to the landing frame for that `(dx, dy)`, computed from the same stepped arc with the hitbox's real extent (the columns touched are `floor((cx-6)/16)` to `floor((cx+5)/16)`, the rows `floor(feet/16)` to `floor((feet+15)/16)`). Over the whole FULL arc the occupied rows per column are: k0 0..3, k1 0..4, k2 3..5, k3 3..5, k4 1..5, k5 0..3, k6 0..1; MID: k0 0..3, k1 0..4, k2 2..4, k3 1..4, k4 0..3, k5 0..1; TAP: k0 0..2, k1 0..2, k2 1..2, k3 0..2, k4 0..1; WALL: k0 0..2, k1 0..4, k2 2..4, k3 2..4, k4 0..3, k5 0..2. The corridor for a specific `(dx, dy)` is the prefix of that up to the landing frame. Note row 5 in columns 2 to 4 of FULL: a full hold needs headroom five rows up, which is why `MID` and `TAP` exist (a 2 up target under a 3 cell ceiling is reached by `MID`, whose corridor tops out at row 4).

### 3.3 Edges

From every standable cell `s`:
1. **WALK**: to `(s.x +- 1, s.y)` if standable. Cost 1.
2. **JUMP(profile, dir, dx, dy)**: to every standable `t` with `dy = s.y - t.y` in `0..JUMP_UP`, `dx = |t.x - s.x|` in `0..maxAcross[profile][dy]`, such that every corridor cell for `(dx, dy)`, mirrored for `dir`, translated to `s`, is open (the target cell and the cell it lands through are excluded; a one way platform cell is open for passage from below), and no one way platform in the descending part of the corridor would catch the hero first (that landing is its own edge, so nothing is lost). Profiles are tried `FULL`, `MID`, `TAP`; the first that clears is the edge's profile. `dx = 0` reaches `dy` up only onto a one way (`plat(t + w)`), since a solid top directly above blocks the body. Cost `2 + dy + dx/2`, plus 3 if the edge sits at the clipped cone's boundary (the planner prefers forgiving edges when it has a choice).
3. **JUMP_DOWN(profile, dir, dx)**: the arc continued below the takeoff row; the target is `FALL_TO(s.x + dir*dx, the row where the arc crosses that column)`.
4. **FALL**: to every standable `t` below `s`: for `t.x == s.x`, every standable cell straight down until the first solid (passing through one way platforms is the hold dive, stopping at the first one is the tap dive or a plain fall; both are the same edge set, the macro differs); for `t.x = s.x +- d`, `d >= 1`, the cells reachable by walking off the edge at full run and falling with the rocker held: `t` standable with the column sweep open where the fall profile (horizontal `RUN`, vertical from 0 at `G` to `TERMINAL`) puts the hitbox, and no standable surface crossed earlier in that path. The harness derives `fallAcross[rowsDown]` the same way as the jump tables (at the frozen numbers: 2 at 1 to 2 rows, 3 at 3 to 4, 4 at 6 to 8, 5 at 12, 6 at 16, 7 at 24). Cost `1 + rowsDown/4`.
5. **WALLTOUCH(side)**: from `s`, to every `wallcontact` or `stickycontact` cell `c` that lies inside some JUMP corridor from `s` (the hero touches the wall mid jump while holding toward it) or inside a FALL sweep from `s`. Cost as the underlying jump or fall + 1.
6. **SLIDE(side)**: from a wall contact `c` to every wall contact `c'` below it on the same wall (same `x`, same `side`, every cell between open and in contact), stopping at the first standable cell, which is also a target (landing after the slide). Cost 1 per row. Sticky contacts do not slide (the fall stops), but the hero may release and drop: STICKY cells get FALL edges like a standable cell (**LET_GO**).
7. **WALLJUMP(side)**: from `wallcontact(c, side)` to every standable `t` with `dy = c.y - t.y` in `0..WALL_UP`, `dx = (t.x - c.x) * (-side)` in `1..maxAcross[WALL][dy]` (always away from the wall), corridor `corridor[WALL]` open; and to wall contacts on the opposite wall inside that corridor (the wall jump chain). Cost `3 + dy` (chain link 4). Never from a sticky contact (DESIGN 4.2: no push off).
8. **STICKYUP**: from `stickycontact(c, side)` to every `stickycontact(c', side)` on the same wall with `c.y - c'.y` in `1..STICKY_UP` and the cells between open (the vine climb, cost 2), and **STICKYTOP**: if the sticky run's top solid cell is at row `t` with `t - 1` within `STICKY_UP` rows above `c`, the cells between open and `standable(c.x + side, t - 1)`, to that cell (the hero pops over the top; cost 3). The model counts no sideways jump off a vine (DESIGN's letter); the sim allows air control after the first frame, which is the generous direction (QUESTIONS Q21).

Every edge records `{ from, to, kind, profile, dir, dx, dy, cost }`. `reach.graph(level)` returns adjacency lists over cell indices plus the standable and contact sets. The graph builds in under 10 ms for a 24x48 room on this box (about 600 standable cells, each with at most 2 + 2*5*6 + fall edges, corridor tests on precomputed cell lists; `H-reach-6`). Reach is symmetric under horizontal mirroring of any room (`H-reach-9`: the model has no handedness).

### 3.4 Clearance test, exactly

`clear(level, cells)`: every cell in the list is in bounds and `solid == 0`. Platforms are open cells and do not block from below. Sticky wall cells are solid and do block. The hitbox is 12 px wide inside a 16 px cell, so a corridor cell list names only the cells the hitbox enters; a one cell wide vertical shaft is passable straight up and the tables account for the 2 px per side of grace. The sim's matching obligation is the ledge nudge: when the hero rises into a solid corner by at most `LEDGE_NUDGE_PX` (2 px) horizontally, the sim slides it sideways instead of bonking (section 3.8, QUESTIONS Q26). The "1 cell per column clearance check" DESIGN names is this per column row span (QUESTIONS Q7).

### 3.5 Biome modifiers

- **Frost (slick)**: a slick platform cell as a landing target is valid only if the sim's one cell slide cannot carry the hero off it: the cell `t + dir` (in the edge's travel direction) is standable, or is solid (the wall stops the slide), or the edge's `dx` is 0. The sim slides exactly `FROST_SLIDE_CELLS * 16` px worth of deceleration and never more, so the one cell margin is always enough. Spawn and the exit are never slick.
- **Deep**: the DEEP tables replace FULL/MID/TAP/WALL (apex +1 cell; falls 20% slower so `fallAcross` grows). Pipes are sticky walls.
- **Overgrowth**: vines are sticky walls. No table change.
- **Ember**, **Attic**: no movement change.
- **Negative** (mode 1): solidity is inverted after the smoothing passes and before the floor and ceiling rules and 6.4, so the floor is still solid and the top still open (QUESTIONS Q20); the tables are the same, the geometry differs. **Double Exposure** (mode 2): `h = 96`, same tables.
- Charms and Skyhook (M2) only ever make the sim more generous (Tripod: wall jump 5 across; Skyhook: +1 up). The model never counts them, so the route score is a promise to a bare hero.

### 3.6 Falls and dives

A fall reaches everything below with clearance (DESIGN 6.8). The model does not distinguish a plain fall, a tap dive (lands on the next surface, one way included) and a hold dive (drops through one ways until released or a solid): all three land on standable cells in the same column set; the bot picks the macro by target: tap dive if `t` is the first platform below, hold dive through `n` platforms if it is the `n+1`th, plain walk off otherwise. A dash never contributes an edge (it stops at the platform edge, DESIGN 4.3).

### 3.7 Exit, repair, enemy envelopes, the main ascent and the route score (DESIGN 6.6, 6.7, 6.9)

**Distances and exit.** `reach.distances(graph, spawn)` is a BFS giving `dist[i]` in edges (`-1` unreachable). The exit (DESIGN 6.6) is the reachable standable cell in rows `0..EXIT_ROWS-1` with the greatest distance, except that the ceiling light (the brightest cluster with L over `CEILING_LIGHT_L` in those rows) wins when its own distance is within `EXIT_LIGHT_SLACK` (2) of the maximum, then by lowest index (QUESTIONS Q11; `EXIT_LIGHT_SLACK: 0` is DESIGN's letter, exact ties only). The beacon sprite is always drawn at the exit cell (`H-feat-7`: exactly one beacon, at the exit; touching it clears the room); when the exit is the light, the light cluster's cells are relit around it, otherwise the light stays backdrop. Every tie in the pipeline breaks to the lowest cell index, lowest palette index or lowest threshold, and every scan is row major from index 0 (Otsu's argmax, equal sized landmarks, equal hue bands, equal bright rectangles, equal widest open runs for spawn, equidistant entries in `nearest`); `H-pipe-11` plants a two way tie in a lab room for each and asserts the lowest wins.

**Repair** (DESIGN 6.7) consumes the same graph: if the exit is unreachable or fewer than `REPAIR_REACH_FRAC` (40%) of **standable** cells are reachable (QUESTIONS Q9), add film tabs: 2 wide one ways along a stair from the reachable frontier cell nearest the largest unreached mass toward it, alternating `TAB_STAIR_ACROSS` (3) across and `TAB_STAIR_UP` (3) up (both inside the main ascent limits, so repaired routes are forgiving by construction), never on a landmark cell or within 1 cell of a landmark top, at most `TAB_MAX` (12), re run reach (the repair loop reuses the graph and rebuilds only the edges whose corridors touch new tabs, so four passes cost well under four graph builds; `H-rep-6`), up to `REPAIR_PASSES` (4); `needsCrop` when the tabs would alter more than `REPAIR_MAX_CHANGE` (15%) of cells or the passes run out. The **default spread** (DESIGN 6.11's last line): when the grid has no landmark and no platform after solidity (a blank wall, all dark, all bright), lay two tab stairs and reserve one speck slot and one fodder slot, so a blank wall still yields a short climb.

**Enemy envelopes** (the cells an enemy can occupy or strike, computed by `features` at placement, used by `safe`): moth, its spawn cell only (it drifts anywhere, so the static rule is the spawn distance `ROUTE_SAFE_ENEMY_DIST`); thorn crawler, every cell of its platform run plus one row above; icicle, its own cell and the column below it for 6 rows; jelly, its column from 2 rows above to 2 rows below its home; spark, its home platform plus every standable cell within 3 cells it can hop to; elite, the pocket interior; trap, its field. A safe cell is outside every envelope and more than `ROUTE_SAFE_ENEMY_DIST` (Chebyshev) from every spawn, so the harness can never pass a room whose every "safe" cell sits on a crawler's patrol (stricter than DESIGN 6.9's spawn distance alone: QUESTIONS Q57, with the corpus count of rooms that change).

**Main ascent.** `reach.mainAscent(graph, level)`: the least cost path from spawn to exit by Dijkstra over the state `(node, wallChain, rowsSinceSafe)` with these filters, each a named reason:
1. `max-range`: a JUMP or WALLJUMP edge `(dx, dy)` is admitted only with at least `ROUTE_SLACK` (1) cell of slack on height **or** distance against the clipped table: `dy + 1 <= maxUp(dx)` or `dx + 1 <= maxAcross(dy)` (DESIGN's letter; with `ROUTE_SLACK_BOTH_AXES: true` both must hold, which is the stricter reading of QUESTIONS Q8; the harness prints how many corpus rooms change under each so Stephen can rule on numbers). WALK, SLIDE, FALL, JUMP_DOWN and sticky edges are always relaxed.
2. `wall-chain`: `wallChain` counts WALLJUMP and WALLTOUCH edges since the last standable node; it may never exceed `ROUTE_MAX_WALL_CHAIN` (2).
3. `safe-cadence`: `rowsSinceSafe` is the row distance climbed since the last safe standable node and may never exceed `ROUTE_SAFE_EVERY_ROWS` (8). Spawn counts as safe. In M0 (no enemies, no traps) every standable non slick cell is safe.
4. Biome rules are already in the edge set (3.5).
5. `enemies-traps` (M1): the edge set is rebuilt after placement; `safe` reflects envelopes; a trap cell is never a node; no corridor crosses a trap cell. Placement forbids enemies within `ROUTE_SAFE_ENEMY_DIST` of the ascent's safe cells and traps on any ascent cell, so the final re check is an assertion of construction, not a second chance.

`reach.routeScore(level, graph, ascent)` returns `{ ok, reasons: [], ascentLength, maxJump: {dx, dy}, wallChains, safeGapRows, hardBranches }`; `reasons[0]` names the first filter that cut the last frontier, with the row it died on, and the harness prints `pipeline.toText(level, ascent)` beside it, so a failing fixture reads like a bug report. Hard jumps and traps are allowed on branches off the ascent that lead to loot; the score never looks there. The exit choice uses graph distance over all edges, not only ascent edges, so a room whose only exit candidate needs a hard jump gets repaired rather than pointed somewhere else.

**The degrade ladder** (QUESTIONS Q36). If the ascent fails at runtime after features are placed (a phone photo can produce a reachable room whose placed enemies or trap break the cadence), the pipeline neither ships an unpassable room nor silently rebuilds it: it removes the enemy nearest the ascent, then the trap field, then runs one more repair pass, then returns `needsCrop` with `why: 'route'`. Each rung is deterministic and logged in `level.degraded`; the harness counts rungs used over the corpus and the morning report quotes the count.

### 3.8 What the sim owes the model (obligations, each a harness assertion)

1. A FULL jump from rest reaches an apex of at least `16*JUMP_UP + 4` px (69.6 at the frozen numbers) and lands on any standable cell the FULL table names, from a centred stance with the rocker held from takeoff. Likewise MID, TAP, WALL, STICKY and the Deep variants. (`H-sim-1`, LAB-EDGE)
2. Landing happens with at least `LAND_OVERLAP_PX` (2) of horizontal overlap with a platform or solid top, on a descending frame, and for one way platforms only when the previous frame's feet were at or above the top. (`H-sim-4`)
3. Ledge nudge: rising into a solid corner by at most 2 px horizontally shifts the hero sideways and continues the rise; by more than 2 px it bonks (`vy = 0`). Descending onto a corner by at most 2 px lands. (`H-sim-5`)
4. Wall slide arms only with at least 14 px of vertical overlap against a solid side and the rocker toward it; it reduces the fall to one third of the current speed, capped at `TERMINAL/3`; releasing the rocker unarms it. Sticky contact arms only on a descending frame (`vy > 0`) after at least one airborne frame; while rising beside a sticky cell the hero is ordinary airborne (otherwise every sticky jump would re stick on its first frame and STICKYUP could never pass). Armed, it stops the fall at zero without the rocker and holds until A, B or rocker away; B or rocker away release it into a plain fall (LET_GO). (`H-sim-10`, `H-sim-11`, `H-sim-12`)
5. Wall jump from an armed slide: `WALL_V` up, 10 frames of locked `WALL_JUMP_PUSH` away, then free air control; facing set away. Sticky jump: `STICKY_JUMP_V` straight up, no lock, air control from frame 2. (`H-sim-9`, `H-sim-15`)
6. Coyote: a jump pressed within `COYOTE` (6) frames of leaving a surface (not by jumping) is a jump; frame 7 is not. Buffer: a press within `BUFFER` (6) frames before landing jumps on the landing frame; 7 does not. Both are what the bot's macros assume when they chain edges without a settle. (`H-sim-2`, `H-sim-3`)
7. Falls reach `TERMINAL` (12 px per frame) in 24 frames; a dive snaps to terminal and zeroes horizontal speed; a hold dive passes through one way platforms while held; a dive that began in the air never becomes a dash on landing. (`H-sim-13`)
8. Dash: 3 cells over 8 frames in the facing direction, i frames for the first 4, stops at a platform edge (the leading foot never leaves the surface), only from a fresh ground press. (`H-sim-14`)
9. Frost: the slide after a landing or stop on a slick surface is at most 16 px. Deep: fall gravity and terminal are `DEEP_FALL_MULT` of base; the jump apex is one cell higher. (`H-sim-16`, `H-sim-17`, M1)
10. Nothing in the sim reads anything but `State`, `Level`, `K` and the input word. `step(step(clone(s), a), b)` equals `step(step(s, a), b)` by hash (no hidden state). (`H-sim-6`)
11. The hitbox is 12x16 in every pose. Air control is instant full run speed (`AIR_CONTROL: 1`) in every airborne state outside the wall jump lock. (`H-sim-18`)

### 3.9 The generosity assertions (the things that can fail)

The sentence in DESIGN 6.8 becomes four harness assertions plus one report. Each builds a room from text (`harness.js`'s `LABS.room(text)`, which constructs a `Level` directly, bypassing the pipeline, so claims are tested on rooms a human can read: `#` solid, `=` one way, `|` sticky, `~` slick, `.` open, `S` start, `X` target), runs the real `SB.sim.step` with a scripted input macro, and compares the hero's resting cell with the model's claim. The macros live in `harness.js`, never in a served block; they may read `state` to time a release (as a player watches the hero), they never write it.

**LAB-EDGE** (`H-lab-1`). For every edge kind and every `(dx, dy)` the tables admit (both directions, every profile, every biome variant), the minimal room: a takeoff cell, the target's support (solid top or one way, as the case names), the wall where the edge needs one, floor and walls far away. Run the macro for at most 120 frames. PASS iff `hero.ground` and the hero's cell is the target (or, for contact targets, the armed slide or sticky contact in that cell). About 140 cases.

**LAB-CLEAR** (`H-lab-2`). For every LAB-EDGE case, for every cell `B` in the bounding box of the move (columns `-1..dx+1`, rows `-1..top+2`: the 12 px hitbox straddles two columns, k6 in the FULL corridor at dx 5) that is **not** in the model's corridor and not the support: add one solid cell at `B` and run the case again. PASS iff the macro still lands on the target. This is "every cell the model does not require to be open is a cell the sim does not need" made testable; it is the assertion most likely to go red the first time, which is the point. About 2,000 runs, under two seconds in Node.

**LAB-NOT** (`H-lab-3`). For every profile, `(dx, maxUp(dx) + 1)` and `(maxAcross(0) + 1, 0)`: run the macro; expect the hero not to reach the target. It proves the sim is not wildly more generous than the model (if it were, the route score's slack would be theatre). WARN on night one, promoted to FAIL in M3 when Stephen freezes `TUNING` (T3.5).

**LAB-ONEWAY** (`H-lab-4`). For every LAB-EDGE JUMP case, for every corridor cell in the descending part of the arc, place a one way platform there and assert the sim lands on it (the model's "would catch the hero first" rule of 3.3 edge 2, frame for frame against the sim's landing rule of 3.8 item 2); for every rising part cell, place one and assert the original target is still reached. Mutant `ONEWAY_CATCHES_RISING`. Without it a model versus sim disagreement on one ways is found only where the corpus happens to hold one.

**BOT-ASCENT** (`H-bot-1`, `H-bot-2`). For every `(fixture, mode, biome)` in the corpus (until `H-sim-17` lands in T1.5 the walk skips the Deep override by name in the output, since the DEEP tables are more generous than the M0 sim; Deep is tested structurally by `H-reach-1b` and `H-reach-7` until then and joins the walk as `H-bot-7`): build, take `ascent.edges`, and for each edge search for an input macro that performs it (section 5.2: for JUMP `(profile, dir, dx, dy)` the candidates are `holdJump` in the profile's frame range, `holdDir` in `0..40`, `delayDir` in `0..8`, ordered by a physics prior with `holdDir` near `dx*16/RUN`, at most 120 candidates, 120 steps each; and per kind: WALL `holdAway` 0..30 after the 10 frame lock; STICKY the `holdJump` range only; FALL `holdDir` 0..60 with `walkOff` 0..8; SLIDE `holdToward` for n rows; WALK one word, so a search miss on those kinds never reads as a generosity failure), re synchronising at every standable node with `settle`. The first success is recorded as the edge's macro (memoised by shape); **if no candidate succeeds, the assertion fails** and prints the fixture, mode, biome, the edge `{kind, from, to, profile, dx, dy}`, the best candidate's final hero cell and the text render with the ascent drawn. Then the walker chains the macros from spawn and asserts arrival at the exit cell. The builder fixes the sim's generosity (the normal case) or the model's claim (only when DESIGN's number is wrong, which is a QUESTIONS entry, never a quiet edit).

**BOT-EXPLORE** (report only). The bot tries every table entry one beyond the model from every standable node of the sample room and prints the extra edges the sim allowed: it tells Stephen how much slack his thumbs actually have.

Scope: `node harness.js` runs LAB-EDGE, LAB-CLEAR and BOT-ASCENT on the main ascent of every level (about 30 edges per level, 200 levels at M1, under 20 seconds on this box); `node harness.js --all-edges` runs the macro search on every edge of every graph (slow gate, before every deploy and in the morning report). Watched red: raise `LAND_OVERLAP_PX` to 8 in a copy (mutant `OVERLAP_8`), or lower `JUMP_V` by 5% (`JUMP_V_LOW`), and the fast run must fail on a four up edge.

**When a lab stays red with nobody to ask** (section 4.0's overrun rule applies here first): after 45 minutes on one red lab case the builder marks that single case `xfail` by name in `harness.js` with a QUESTIONS entry naming it, keeps the rest of the gate live, writes BLOCKED in PROGRESS, and continues; the morning report lists every xfail. `TUNING` movement numbers may be retuned to turn a lab green (the normal fix at 2 a.m.); the tables are never hand edited.

## 5. Test plan

### 5.1 The harness: `node harness.js`

One file, Node built ins only, CommonJS (an ESM `.js` without a `package.json` prints a MODULE_TYPELESS warning above every gate table; the fleet learned that in gerplunk). It loads the core from `index.html` (section 1.3), loads every fixture under `fixtures/` (`sample-room.json`, `synthetic/*.json`, `rooms/*.json` for Stephen's rooms, picked up by directory), and runs the matrix **fixtures x modes x biomes**: every record in mode 0 and mode 1 (Negative, live from T0.6; mode 2 fixtures run as themselves), each under the five biome overrides plus "as detected" (reach and the route score for every override from T0.10a; the bot's walk skips the Deep override, named in the output, until T1.5 gives the sim Deep gravity, since the DEEP tables are more generous than the M0 sim) (so DESIGN 13.1's 20 grids x 5 biomes x Negative on and off is a subset of what runs; with the synthetic twenty standing in for Stephen's twenty until they arrive, then both, QUESTIONS Q45). For each built level it computes `levelHash`, the reach graph, the main ascent, the route score, the feature placements, the fixture's `expect`, the bot's walk and the walk's state hash, and it prints the time.

Output: one line per assertion group, the failing lines in full (never the tail: the tail of a gate that died on assertion three is twenty five green ones), the text render of the room beside every level or bot failure, and `SHUTTERBUG HARNESS OK` only when everything ran and the assertion count met `ASSERT_FLOOR`; with xfails, `SHUTTERBUG HARNESS OK WITH N XFAIL` and the list. `--fast` skips `--all-edges` and `--economy` and says so.

```
node harness.js                      everything: known answers, labs, corpus x modes x biomes, bot, replays, perf
node harness.js --fast               the per task run (under 60 s on this box at M0)
node harness.js --page <file>        the same against another copy of the page (what redwatch and the deploy check use)
```

### 5.2 The bot

The bot is the harness's player. It never reads the render; it reads `State` and drives `sim.step` with input words.
1. **Plan**: `reach.mainAscent` gives the edge list from spawn to exit.
2. **Macro per edge**: section 3.9's search, memoised per `(kind, profile, dir, dx, dy, biome)` plus a geometry signature of the corridor (a macro found once on a shape is reused on the same shape elsewhere; the search runs only on new shapes). A miss on a memoised macro falls back to a fresh search before it counts as a failure.
3. **Settle** between edges: after a landing, hold the rocker toward the cell centre until the hitbox centre is within 2 px of it, then release and wait for `vx == 0` and grounded; at most 30 steps or the settle fails (and that is a sim bug: a hero that cannot stand still in a cell).
4. **Walk**: chain the macros; after the last, assert the hero is in the exit cell. The concatenated words are the walk's replay script.
5. **Enemies** (T0.16 on): before each edge the bot waits up to 600 frames for no enemy within 2 cells of the source and the corridor; a timeout FAILS. Contact damage during an edge is allowed (the ascent is a route, not a no hit run); the bot is immortal for route walks (`opts.immortal = true`) and mortal only for `H-en-3`, which asserts hearts at least 1 at the exit on the sample room with the first room cap (QUESTIONS Q30).
6. **Random edges**: 200 edges per level drawn from the full graph with `mulberry32(seedOf(record) ^ 0x5bd1e995)`, each executed from a state with the hero placed on the source (the fast run takes 20 per level; `--all-edges` takes every edge).
Failure output names the fixture, mode, biome, the edge index and shape, the macro tried, the hero's final cell and the text render with the ascent and the offending cell drawn.

### 5.3 The route score

`reach.routeScore` as section 3.7, reported per level as `{ ok, reasons, ascentLength, maxJump: {dx, dy}, wallChains, safeGapRows, hardBranches, tabs, degraded }` and summarised over the corpus in the harness output (median ascent length, the repair tab distribution, the count repaired, the count `needsCrop`, the count that changes under `ROUTE_SLACK_BOTH_AXES`, the degrade rungs used, and the level length proxy: the bot's walk frames divided by 60 per level, an optimal walk a player takes two to four times longer than, median and p95 over the corpus, flagged when the median is under 15 s or over 60 s against DESIGN 5.1's 60 to 120 s target). The summary is what Stephen reads to judge whether rooms feel climbable before he plays them; the morning report quotes it.

### 5.4 Determinism replay

Three layers, each a test that can fail:
1. **In Node** (`H-sim-6`, `H-bot-3`, `H-bot-4`): a 3600 step seeded random script and the bot's own walk run twice from fresh states and in two fresh `vm` contexts; the hashes are compared at every 100th frame (so a divergence is located, not merely detected) and at frames 300, 900, 1800 and the end; a structured clone is stepped in lock step; flipping one input bit at frame 100 changes the final hash (a hash that cannot change is not a hash).
2. **Golden**: `fixtures/replays/*.json` hold the bot's walk and its hash per fixture, mode and biome; any change to the sim, the tables, the features or the RNG changes a hash and the harness fails until `--regold --why` is run on purpose, with the why in the file and in PROGRESS.md.
3. **Cross engine** (T3.5): the page runs the same scripts through `SB_DEV.replay(script)` (a fresh sim, no render) and must produce Node's hash. Node and Chrome are both V8; the iPhone runs JavaScriptCore, so the settings screen shows the last replay hash on its `Performance` line and the phone matrix row compares it with Node's by eye, with no DevTools. Because `State` is all integers and the hash is over typed bytes (section 2.5), the only ways this fails are a DOM, timer or `Math.random` leak into the sim, a non correctly rounded `Math` call, or a screen dependent field in `State` (there is none: the camera lives in `render`, section 1.5, so a 22 row SE and a 40 row Pixel hash alike), which is exactly what the poison prelude, the lint and `H-sim-7` exist to catch.

Coverage (`H-sim-7`): every `FIELDS` entry perturbed, key lists equal, no undeclared key after 600 steps; `serialize` throws on a float naming the path; a count of floats met is printed every run.

## 6. Risks the lead sees that DESIGN does not cover, with a recommendation each

1. **Phones narrower than 384 CSS px.** The 1 game px = 1 CSS px rule cannot hold on a 360 wide phone, and "centre with side gutters" assumes the world fits. 2. **Short phones.** 36 + 640 + 168 = 844 fits one phone exactly. Recommendation: `VIEW_ROWS` 28..40 with the strip never shrinking and the camera keeping the hero at 60% of what is visible (Q6).
3. **Frost cannot be detected by the saturation rule.** White and light grey have saturation near zero, so DESIGN 6.10 can never say Frost. Recommendation: fewer than 10% saturated cells and a mean palette L over 170 is Frost, else Attic (Q4).
4. **The jump cone is a box, not a corner.** 4 up and 5 across are not reachable together under any physics with a 4 cell apex and a 34 frame hang. ### 7.2 Biome index bands (DESIGN 6.10 in palette terms)

Saturated entries (`SAT`): Walnut, Amber, Brick, Magenta, Lapis, Teal, Moss, Sun. Bands: **Attic** = {Walnut, Amber, Sun} (warm, hue 10..70), **Ember** = {Brick, Magenta} (hue 300 or more, or under 10), **Deep** = {Lapis, Teal} (hue 160..260), **Overgrowth** = {Moss} (hue 70..160). Fewer than 10% of cells in `SAT` at all: **Frost** if the mean palette L of all cells exceeds `FROST_MEAN_L` (170), else Attic (QUESTIONS Q4). Film and the greys never vote; Ink's HSV saturation (0.33) is under the threshold and it is not in `SAT`, so a tinted near black never counts as blue.

Two consequences of reading DESIGN 6.11 through the palette (QUESTIONS Q12): a **loot speck** source cell is an isolated **Sun** cell (index 14), because only Sun satisfies S over 0.5 and L over 150 (Amber is L 143, Teal L 147); Amber and Teal cells are not loot (QUESTIONS Q49). And since `SAT` holds Walnut and Sun, **enemy clusters** are formed only after the beacon's cells, the door's cells, the speck cells and the cells of every solid landmark leave the saturated set, and a cluster on other solid cells spawns beside itself on the nearest standable open cell outside the ascent's safe set (QUESTIONS Q50): a brown bookshelf is a landmark, not a nest, and the lamp is the beacon, not a moth.

### 7.3 Solid, open and platform triplet per biome, and the contrast rules

The backdrop is the quantized photo blended 40% toward Pewter (DESIGN's 60% contrast): `open(idx) = mix(palette[idx], Pewter, 0.4)`; `solid(idx) = open(idx) * 0.6` plus a 1 px Ink outline. Each biome then tints: solid cells 35% toward the biome's solid colour, open cells 20% toward its open colour, and draws its platform line under the Glare top edge. The render snaps nothing back to the palette for the backdrop (it is a dimmed photograph); every sprite, edge and tab is drawn in palette colours, which is what the `sprites` gate samples.

| Biome | Solid tint | Open tint | Platform line (under Glare) | Danger and extras |
| --- | --- | --- | --- | --- |
| Attic | Walnut | Ash | Amber | moth Ash with an Ink outline; dust motes in Film (cosmetic) |
| Frost | Slate | Paper | Pewter; slick surfaces get a Teal ice edge | icicles Ash with Glare tips; crushers Slate with a Brick stripe and Glare teeth |
| Deep | Lapis | Slate | Teal | jelly Teal with a Magenta core; pipes Teal with Ink rings |
| Overgrowth | Moss | Ash | Walnut | thorn crawler Moss with Brick thorns and Glare tips; vines Moss with Ink stems |
| Ember | Soot | Pewter | Amber | spark Brick with a Glare core; spikes Brick over Ink |

Contrast, computed (WCAG relative luminance on this box): after the blend the open backdrop spans luminance 0.048 (Ink cells) to 0.620 (Glare cells) and solids 0.019 to 0.202. No single colour clears 3:1 against that whole range, so the rule is **two tone everywhere**:
- **Collision edges** are Glare over Ink (two 1 px lines). Ink clears 3:1 against any backdrop above luminance 0.109; Glare clears 3:1 against any below 0.289; the ranges overlap, so one of the two lines always clears 3:1 against the cell on either side. `H-pal-3` computes exactly this.
- **The hero** is Sun fill with an Ink outline, an Ink feet row and a Glare eye: Sun clears 3:1 below 0.183, Ink above 0.109, overlap again; Sun against Brick is 3.56:1 and against Magenta 2.79:1, which is why enemies never share the hero's outline weight: they get an Ink outline plus a Glare highlight pixel and they move, and the hero is the only Sun sprite. The feet row is Ink because the feet sit on platform edges that are Glare, Amber, Teal or Walnut, all over 3:1 against Ink.
- **Danger** is Brick and Magenta fills with an Ink outline and Glare tips; the dimmed backdrop never shows them at full strength (the blend pulls every photo red toward Pewter), so a fully saturated red or magenta pixel on screen is always a sprite or a trap.
- **Repairs** are Film, which sits far from every surface colour (7.97:1 against the darkest open cell) and is used by nothing else and never produced by the quantizer, so help is never mistaken for furniture; on Frost the perforation is Ink and the tab reads by its edge.
- **Loot** is Amber with a Glare glint; Sun is reserved for the hero, the chest trim and the beacon so a speck never reads as the player.

Highest contrast therefore belongs to collision surfaces (Glare over Ink) and to danger (saturated over Ink with Glare), as DESIGN 3 requires; the backdrop never competes because the blend caps its range. The readability script (section 5.9) is the judge the numbers cannot replace.
